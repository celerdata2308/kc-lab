一、用户画像 (User Personas)

1.1 企业级 SaaS 平台 — 嵌入式分析型

EMBEDDED ANALYTICS

将 StarRocks/CelerData 作为 SaaS 产品的分析引擎，直接面向终端用户提供数据洞察。核心诉求是低延迟查询 + 高并发 + 多租户隔离。

代表客户: Demandbase Clio BambooHR Herdwatch

  • Demandbase (ABM 平台): 从 Druid 迁移。为 B2B 营销客户提供实时 account-level analytics。对 sub-second 延迟和千级并发有硬性要求。
  • Clio (法律 SaaS): 替代 Trino/Athena。核心需求是简化 pipeline（去 Flink）和 MySQL 兼容性。
  • BambooHR (HR SaaS): 从 Snowflake 迁移。驱动力是成本优化和查询延迟改善。
  • Herdwatch (农业 SaaS): 从 BigQuery 迁移。核心需求是成本效率和 real-time ingestion。

画像特征: 团队 2-5 人 · 数千-数万终端用户 · TCO 驱动 · 延迟 <100ms p99 · 替代 Druid/Trino/Snowflake/BigQuery

1.2 超大规模平台 — 基础设施型

INFRASTRUCTURE

CelerData 最大的企业客户群，StarRocks 在其基础设施中承担关键数据服务角色。需求复杂度和运维要求极高。

代表客户: Intuit (含 Mailchimp) Expedia Coinbase Pinterest

  • Intuit: 最大客户。已历 S0 事故（24h 宕机）+26 个 S1/S2。需求包括 Flink 多表事务 (POST-997)、Multi-AZ (POST-1121)、Lake Formation (POST-1018)、扩缩容优化 (POST-1120)、配置暴露 (POST-1199)、Agentic AI 探索。
  • Expedia: 4 个并行 initiative — sugarBI、TPSP、EGMP、EGAP。多团队多场景。
  • Coinbase: 替代自建 Postgres+Redis。核心需求是实时性和高并发。
  • Pinterest: 为广告主提供 campaign analytics。关键需求是 Iceberg 集成和查询性能。

画像特征: 团队 10-50+ 人 · PB 级数据 · SLA 99.99%+ · $100K-500K+/月 · 需要 Multi-AZ HA

1.3 金融 / 受监管行业 — 安全合规型

COMPLIANCE

中国金融机构客户群，对安全、权限、审计有极高要求。部署通常在私有云或混合云环境。

代表客户: 光大银行 华润信托 微众银行

  • 光大银行: LDAP+Stream Load 认证、Debezium Routine Load (Avro)、Kerberos 多 Catalog、Manager 并行启停和断点续传。
  • 华润信托: 用户级别资源隔离监控（非 Resource Group 级别）。
  • 微众银行: 物化视图数据质量问题 (SR-34319)。

画像特征: 私有云/混合云 · LDAP/Kerberos/Ranger · 等保三/四级 · SOC2 · 数据不出境

1.4 高增长科技公司 — 敏捷分析型

HIGH GROWTH

快速增长的科技公司，数据规模急剧扩大，需要分析基础设施跟上业务增长节奏。

代表客户: Kaspi BingX Eightfold AI Celonis

  • Kaspi: 22K+ 张表。StarRocks Catalog 跨集群查询、全局索引可见性、Resource Group 展示优化。
  • BingX: Warehouse 熔断机制 (SR-35649)，防止大查询影响稳定性。
  • Eightfold AI: AI 集成能力和实时人才分析。
  • Celonis: 大规模 process mining 数据分析性能。

画像特征: 月增 20-50% · 存算分离偏好 · K8s 原生 · API 优先 · $10K-100K/月

二、Use Cases and User Stories

2.1 嵌入式实时 Dashboard

SaaS 产品将 StarRocks 驱动的分析仪表盘嵌入其应用，终端用户通过 Web UI 查看实时数据洞察。

"作为 Demandbase 的 B2B 营销经理，我需要实时查看 target account 的 engagement score 和 intent signals，以便在客户有购买意向时及时跟进。查询响应必须在 1 秒内。"
"作为 BambooHR 的 HR 主管，我需要按部门查看员工离职率、薪酬分布等人力分析，支持下钻到个人级别。"
P99 < 100ms 1000+ 并发 多租户 RLS MySQL 兼容 API/JDBC

2.2 实时数据管道 (无 Flink 架构)

利用 StarRocks 的 Routine Load、Stream Load 直接从 Kafka 消费数据，无需维护 Flink 集群。

"作为 Clio 的数据工程师，我需要将案件事件流从 Kafka 实时写入 StarRocks，而不需要维护 Flink 作业，因为我们的小团队没有流处理专家。"
"作为光大银行的数据平台运维，我需要通过 Debezium CDC + Routine Load (Avro) 将 Oracle 变更实时同步到 StarRocks，且认证必须与现有 LDAP 体系打通。"
Routine Load Debezium Avro LDAP/Kerberos 认证 断点续传 Exactly-Once

2.3 Lakehouse 联合分析

在数据湖 (Iceberg, Delta Lake) 中存储历史冷数据，用 External Catalog 联合查询热温冷数据。

"作为 Intuit 的平台架构师，我需要通过 AWS Lake Formation 统一管理 StarRocks 对 S3 数据湖的访问权限 (POST-1018)，确保合规审计。"
"作为 Kaspi 的数据团队 lead，我需要用 StarRocks Catalog 跨集群查询 22K+ 张表，实现不同业务域数据的联合分析。"
External Catalog Lake Formation Iceberg Compaction StarRocks Catalog

2.4 多租户运营与资源隔离

为不同租户/业务线提供独立的计算资源和数据隔离，保持运维统一性。

"作为 Expedia sugarBI 的平台负责人，我需要为不同酒店合作伙伴提供独立的分析环境，确保查询性能互不影响。"
"作为 BingX 的 DBA，我需要 Warehouse 熔断机制，当某个大查询消耗过多资源时自动限流。"
RLS / Schema / DB 隔离 用户级资源监控 Warehouse 熔断 弹性扩缩容

2.5 企业级高可用与灾备

关键业务负载要求多可用区容灾、自动故障转移、零停机升级。

"作为 Intuit 的 SRE 负责人，经历 S0 事故（24h 宕机）后，我需要 Multi-AZ 部署 (POST-1121) 确保单个 AZ 故障不影响业务。"
Multi-AZ (4.0) DW HA (SR-37274) Cache-Aware Scaling 跨集群复制 (POST-634)

2.6 安全、权限与合规

与现有企业身份管理系统集成，支持细粒度权限控制，满足行业监管要求。

"作为光大银行的安全管理员，我需要 StarRocks 与 LDAP/Kerberos 统一认证，包括 Stream Load 接口。"
LDAP/Kerberos 全链路 Ranger RBAC SAML 2.0 SOC2 审计日志

2.7 Agentic AI 与智能分析 (新兴)

将 LLM/AI Agent 与 StarRocks 集成，实现自然语言查询、智能告警、自动化分析报告。

"作为 Intuit 的 AI 产品经理，我需要让 AI Agent 通过自然语言查询 StarRocks 数据，为 QuickBooks 用户自动生成财务洞察报告。" (Intuit 已在讨论 Agentic AI use cases)
Text-to-SQL / NLQ information_schema Vector Search Streaming 结果 Python UDF

三、用户痛点 (User Pain Points)

3.1 稳定性与可靠性 (P0 — 最严重)

多个大客户遭遇严重生产事故，直接威胁客户关系和合同续约。

  • Intuit S0 事故: 24 小时完全宕机。事后暴露代码质量问题。近期还有 26 个 S1/S2 事件。
  • Intuit Mailchimp 生产事件: 导致 SA/SE 交接流程和跨团队事故协调改进。
  • 扩缩容性能降级 (POST-1120): 集群扩缩容期间查询性能显著下降。

影响范围: 所有大型企业客户 · 建议: P0 — 必须在 2026 H1 全面解决

3.2 运维复杂度 (P1)

集群运维操作不够自动化和透明，需要大量手动干预。

  • 配置管理不透明 (POST-1199): Intuit 紧急要求。
  • Manager 并行启停: 光大银行，当前串行执行效率低。
  • 断点续传缺失: 大规模加载中断后需从头开始。
  • 存算分离采纳难: 很多中国客户缺乏对象存储基础设施。

3.3 多租户与资源管理不足 (P1)

现有 Resource Group 机制粒度不够，无法满足精细化多租户管理需求。

  • 用户级资源监控缺失 (华润信托)
  • Warehouse 熔断缺失 (BingX, SR-35649)
  • 22K+ 表元数据管理 (Kaspi)
  • 多租户实现标准缺失 (SR-36910)

3.4 数据质量与一致性 (P2)

  • 物化视图数据不一致 (微众银行, SR-34319)
  • Flink Connector At-Least-Once (POST-997, Intuit)
  • 权限规划不完善 (SR-36856)

3.5 生态集成不足 (P2)

  • AWS Lake Formation 未打通 (POST-1018, Intuit)
  • LDAP/Kerberos 全链路 不完整 (光大银行)
  • SAML 2.0 for Manager 缺失 (多客户)
  • Python UDF 多客户需求

3.6 存算分离成熟度 (P2)

  • 客户采纳障碍: 缺乏对象存储基础设施 (中国市场)
  • Cache 管理: CNGroup cache 和 cache replica 问题 (Intuit)
  • Multi-AZ 缺失: 4.0 才规划 (POST-1121)
  • 跨集群复制 未完成 (POST-634)

4.2 竞争格局变化

ClickHouse — 开源霸主策略

2024 年估值 $150 亿。推出 chDB（嵌入式 ClickHouse），可嵌入 Python/Go/Node.js。开源社区势能强劲。

⚠ 对 CelerData 的威胁: 在开发者市场和中小客户群有替代风险

Snowflake — AI 原生转型

推出 Cortex Agents (LLM 数据分析 Agent) 和 Native Apps (第三方分析应用分发)。从 Data Warehouse 向 Data Cloud + AI Platform 转型。

💡 启示: 平台化和 AI 集成是大势所趋

Databricks — 嵌入式仪表盘

推出原生嵌入式 Dashboard，按计算量计费（非按用户数）。Lakehouse 架构深化 (Unity Catalog, Delta Lake 4.0)。

💡 启示: 计算模型定价更适合嵌入式分析场景

Apache Pinot / StarTree · Rockset → OpenAI

StarTree 商业化加速，最直接的技术竞品。Rockset 被 OpenAI 收购，验证了"实时分析 + AI"的融合趋势。

4.3 关键技术趋势

4.3.1 Agentic Analytics (AI Agent 驱动的分析)

2026 年最重要的行业趋势。传统 BI dashboard 正在被 AI Agent 增强甚至替代。

  • Text-to-SQL / NLQ: 自然语言 → SQL → 可视化
  • 自主分析 Agent: 主动发现数据异常和趋势
  • 对话式分析: 多轮对话式数据探索
  • 行业案例: Intuit 已在内部讨论 Agentic AI use cases

4.3.2 真正的多租户 (True Multi-Tenancy)

模式隔离级别适用场景代表厂商做法

4.3.3 Data Apps · 4.3.4 性能基准提升

嵌入式分析从"看板"进化为产品核心功能。行业性能期望持续提升:

P99 < 100ms (Must have) 1000+ 并发 (基本要求) 秒级数据新鲜度 扩容 <60s 开始服务

  • 跨 Shared Data 集群复制 (POST-634) 未完成

建议: Multi-AZ + graceful scaling 是 4.0 must-have
P2

Gap 4: 数据治理与血缘 (Data Governance & Lineage)

现状: AuditLoader 审计日志可用。无原生数据目录或血缘追踪。

竞品: Databricks Unity Catalog 提供跨工作区数据发现、列级血缘、标签管理。Snowflake 有 Access History 和 Object Dependencies。

差距: 列级血缘 · 数据分类标签 · 数据质量指标 · 统一目录
建议: 先做轻量级 table→table 血缘和 data classification tags
P1

Gap 5: 安全认证全链路覆盖 (End-to-End Auth)

现状: v3.5 JWT/OAuth, LDAP 基础集成, Ranger RBAC。

  • Stream Load 缺少 LDAP 认证 (光大银行)
  • Kerberos 多 Catalog 认证未完善 (光大银行)
  • AWS Lake Formation 权限未打通 (Intuit POST-1018)
  • SAML 2.0 for Manager 缺失 (多客户)
  • Masking Policy 展示不完整 (SR-36131)
影响客户: 光大银行 (4项) · Intuit · 多个中国金融客户
建议: 先解决光大银行 LDAP 全链路，再推 Lake Formation
P2

Gap 6: 嵌入式模式 (Embedded Mode)

StarRocks 是分布式集群架构，无单进程嵌入模式。竞品 ClickHouse chDB 和 DuckDB 在开发者社区获得极大关注。

差距: 无法作为 library 分发 · 无 WASM · 无单机模式
建议: 长线规划，2026 不急于投入
P2

Gap 7: 原生调度 (Native Task Scheduling)

现状: MV 有 REFRESH ASYNC EVERY 调度，无通用 task scheduler。竞品 Snowflake Streams & Tasks 提供原生 CDC + 调度编排。

差距: 客户必须依赖 Airflow/Prefect 等外部工具
建议: 可在 MV 调度基础上扩展为通用 task 调度
